# AGENTS.md — Conventions for agents working in this repo

This repo is a reusable library of devcontainer **features** (`src/features/*`)
and **templates** (`src/templates/*`), published under the `docker-x/devcontainer`
namespace via the devcontainers/action release workflow. Features are consumed
by many downstream projects — correctness and convention matter more than
expediency.

## Repo layout

```
src/features/<id>/
  devcontainer-feature.json   # metadata, options, dependsOn, installsAfter
  install.sh                  # build-time install script (runs as root)
  README.md                   # auto-generated by release workflow — do NOT hand-edit
src/templates/<id>/
  devcontainer-template.json
  .devcontainer/...
.github/workflows/release.yaml  # publishes features + templates on main
```

## Writing / modifying a feature

### `devcontainer-feature.json`
- `id` must match the directory name.
- `version` is semver — bump on **any** published change (patch for fixes,
  minor for additive, major for breaking option removal/renaming).
- Declare `dependsOn` for features this one needs at runtime (e.g. most agent
  features depend on `ghcr.io/docker-x/devcontainer/agent-config`).
- Declare `installsAfter` so the build order is deterministic — include
  `ghcr.io/devcontainers/features/common-utils` and `.../features/node` when
  the install script needs a shell + Node.
- `documentationURL` should point to the upstream tool, not this repo, unless
  the feature is repo-specific.

### `install.sh`
Every install script in this repo follows these conventions — match them:

- Start with `#!/bin/bash` + `set -e`.
- Resolve the remote user and home portably:
  ```bash
  REMOTE_USER="${_REMOTE_USER:-${_CONTAINER_USER:-root}}"
  REMOTE_USER_HOME="${_REMOTE_USER_HOME:-$(getent passwd "$REMOTE_USER" 2>/dev/null | cut -d: -f6)}"
  REMOTE_USER_HOME="${REMOTE_USER_HOME:-/home/vscode}"
  ```
  This `${a:-${b:-c}}` chain is correct here because these vars are *unset*
  when not provided — unlike `HOME` (see Lessons below).
- Download binaries to a `mktemp -d` directory, not a fixed path (CWE-377).
- Verify downloaded artifacts with SHA-256 before executing (CWE-494). See
  `src/features/devsy/install.sh` for the pattern.
- Expose installed binaries globally via `ln -sf ... /usr/local/bin/<name>`.
- Put env exports in `/etc/profile.d/<feature>.sh` (chmod 0755) **and**
  `/etc/environment` for non-login shells.
- Share config across agent features via `AGENT_CONFIG_DIR`:
  ```bash
  AGENT_DIR="${AGENT_CONFIG_DIR:-/usr/local/share/agent-config}/<id>"
  ```
  Then symlink `$REMOTE_USER_HOME/.config/<id>` → `$AGENT_DIR` so per-user
  tools find a shared, PVC-safe config.
- Run user-scoped install steps as the remote user (`su -s /bin/bash -` or
  `sudo -u`), not as root, so file ownership is correct.
- Keep `apt-get` calls consolidated: one `apt-get update`, one
  `apt-get install`, one `rm -rf /var/lib/apt/lists/*`.

### READMEs
`README.md` under each feature is **auto-generated** by the release workflow
(`devcontainers/action` with `generate-docs: "true"`). Do not hand-edit —
describe the feature in `devcontainer-feature.json` and let the generator
produce the README. The release workflow opens a PR with the regenerated docs.

## Release flow

- Publishing is manual: `workflow_dispatch` on `.github/workflows/release.yaml`,
  only runs on `main`.
- The action publishes to GHCR under `ghcr.io/docker-x/devcontainer/<id>` and
  opens a docs PR with regenerated READMEs.
- There is no CI that runs `install.sh` on PRs — test locally with
  `devcontainer build` or by sourcing the script in a matching base image.

## Lessons hard-won from incidents

### `${HOME:-fallback}` is wrong when the var may be set to a bad value
OpenShift restricted SCC sets `HOME=/` for random-UID containers. A
`${HOME:-/home/vscode}` fallback only substitutes when `HOME` is *unset*,
not when it is `/`. This caused 6 Devin sessions to be written to ephemeral
`/.local/share/devin/` and lost on pod recreation (Aug 2026).

**Rule:** in entrypoints and runtime scripts, assign unconditionally:
`export HOME="/home/vscode"`. The `${a:-${b:-c}}` chain above is fine for
`_REMOTE_USER` etc. because those are genuinely unset when absent — `HOME`
is the exception because OpenShift actively sets it to a bad value. Same
applies to any env var a restricted SCC may set to a surprising value
(`XDG_*`, `TMPDIR`). Exception: in documented local-only debug contexts,
`:-` fallbacks are acceptable.

### Verify actual write paths before recreating pods
Before any pod/container recreation, confirm tools write where you think:
1. `echo "$HOME"` — must be the PVC-backed home, not `/`. If it is `/`, **stop and alert a human** before proceeding.
2. `du -sh ~/.local/share/<tool>/` — confirm the path is non-empty and on the PVC.
3. `readlink -f ~/.local/share/<tool>` — confirm the symlink target is on the PVC.
4. Confirm the backup source path matches the *actual* write path from step 3.

### Persistence stores are independent
"Paseo agent metadata survived" does NOT mean "Devin sessions survived."
Each tool has its own store — check them independently after pod recreation:
- Paseo: `/workspace-state/.paseo/agents/` (PVC)
- Devin sessions: `~/.local/share/devin/` (PVC only if `HOME` is correct)
- Source: PVC + git remote
- Devin config + `gh` auth: PVC

### Backups cover the PVC, not ephemeral storage
Backups capture `/workspace-state/` (PVC). Any tool writing outside that path
is NOT backed up. Before adding a tool that writes to `~`, verify its write
path lands on the PVC via the symlinks in `/workspace-state/home-links/`.

The full postmortem for the session-loss incident is in git history:
`git show b88906e:RETROSPECTIVE-devin-session-loss.md`.
